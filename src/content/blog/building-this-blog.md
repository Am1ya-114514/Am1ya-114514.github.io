这个站不是从零写的，起点是一份别人开源的 Astro 博客主题。把别人的项目改成自己的东西，最麻烦的其实不是改样式，而是**搞清楚哪些东西是骨架、哪些只是原作者的私人内容**。

下面是我实际动过的地方，留个记录。

## 一、先确定技术底座

静态输出，构建时把 Markdown 编译成 HTML，不依赖运行时服务。文章目录约定 `src/content/blog/*.md`，用 Content Collections 校验 frontmatter，字段是固定的：

```yaml
---
title: "标题"
description: "摘要"
pubDate: 2026-10-12
updatedDate: 2026-10-12
cover: "/blog-covers/cover-01.webp"   # 可选
tags: ["Astro", "Frontend"]
category: "tech"                      # tech | anime | life
draft: false                          # 可选
---
```

`category` 只有三个取值，多了会在构建时直接报错，算是给自己留的一道约束。

## 二、把多主题拆成单主题

原主题带了三套皮肤，靠一个注册表在前端切换，存储键是 `yuimi-theme-id-v2`，默认皮肤挂在根路径，其余皮肤挂在 `/themes/<id>/` 下面。

我只要一套，所以：

1. 删掉另外两套皮肤和它们的路由副本；
2. 把注册表改成只声明一项，并且**不给它 `routePrefix`**，于是主题直接挂在站点根；
3. 删掉前端主题切换组件和右键菜单里的切换按钮；
4. 保留长按/右键唤出快捷菜单的能力——它和主题选择本来就不是一回事。

这一步最容易踩的坑是：主题路由前缀不只是一个字符串，它同时出现在页面路径判断、sitemap 过滤、以及若干测试断言里。少改一处，页面看起来正常，但某个角落会悄悄指向一个 404。

## 三、换掉所有属于原作者的痕迹

站点名、昵称、简介、社交链接、项目列表、导航文字，这些都要换成自己的。

这里有个判断值得记下来：**哪些标识符该改名，哪些不该**。

- 用户能看见的文案：全改。
- 内部标识符，比如 `data-yuimi-*`、`window.__yuimi*`、`yuimi-radio-state-v1`：**不改**。它们对访问者不可见，却同时散落在 CSS、脚本和测试里，重命名只有装饰价值，风险却实打实。

## 四、生成的手写字标

首页那个手写标题不是图片，是一段 SVG：把字体里的字形轮廓取出来，用描边动画一笔一笔"写"上去。

原来的字标烘焙的是原作者的名字，得重新生成。生成脚本改了两处：

- 笔迹遮罩不再硬编码每个字母的笔画，而是直接拿字形自己的轮廓去描边，这样标题文案可以随便换；
- `viewBox` 改成按所有字形的墨迹包围盒计算。原来的标题里没有下伸字母，盒子高度是拍脑袋定的；新标题里有 `y`，不重算就会把尾巴裁掉。

第二点是渲染出来才发现的——**生成的图形一定要实际看一眼**，别只看代码有没有报错。

## 五、让构建真的能过

原项目的构建流程里有一个"性能预算"检查脚本，里面写满了针对那套被删掉的主题的断言。单主题化之后它必然失败。

重写的时候我把检查换成了跟主题无关的指标：每个页面的 HTML 体积、每个页面实际加载的样式总量、所有 JS chunk 的总量和最大单块，再加上一条针对本站的回归保护——**手写字标的 `viewBox` 宽高比必须和 CSS 里给它的盒子一致**，否则字会被压扁或者留白。

## 小结

把别人的项目变成自己的，工作量的大头在"减法"和"清理引用"上，写新代码反而是最少的部分。做完之后，整个仓库里应该找不到一句属于原作者的自我介绍——包括那些藏在文档和配置里的。
